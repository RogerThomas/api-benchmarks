### Breaking change caught: `jero` 0.0.27 → 0.0.53

`jero` is pinned as `>=0.0.27` (floating), so this refresh pulled 0.0.53. Two renames
broke the app on startup:

- `Factory.enter` / `Factory.aenter` → `Factory._enter` / `Factory._aenter`
- `App.include_endpoint` / `App.include_resource` → `App._include_endpoint` / `App._include_resource`

Both are meant to be called from within a subclass (that's why they're prefixed) — fixed
all four call sites in `jero_app.py` to match. No other app touches these.

## Caveat: this run saturates every physical core on the host

The M3 Max host has 14 physical cores (10P + 4E), and this run's `cpuset` map commits
all 14 to Docker: 8 frameworks (0–7) + Postgres (8,9) + upstream (10,11) + runner (12,13).
With gin/elysia previously disabled, one core (6) sat idle and only 6 framework
containers were ever alive at once; now all 8 are alive simultaneously (only one under
active load at a time, the rest idle), and every core is spoken for.

That leaves **zero spare host capacity** for the macOS side of Docker Desktop (VM
management, WindowServer, this very shell). It shows up as a systemic throughput drop
across every single framework compared to a narrower run: rerunning just jero vs
fastapi in isolation (4 containers alive, not 11) measured jero at **56.9k req/s** on
test 1 vs **48.3k** here — a ~15% drop, and gin/elysia/jero's compiled-vs-interpreted
*relative* gap moved too (gin/elysia only just overtook jero on test 1 here, at VUS=100
they were further ahead in v2 at VUS=128).

The relative comparison across frameworks in this run is still fair — every framework
sits under the identical 8-containers-alive contention. But it's not directly comparable
to older reports run with fewer containers alive, and it's not the noise-free ceiling
either framework could reach standalone. If you want the clean ceiling per framework,
run a subset (e.g. `FRAMEWORKS="jero fastapi" task test` after `docker compose up -d`
just those two + infra) rather than the full 8.

# jero-benchmarks — final run v3, 2026-07-19 (Python 3.13.14 · Robyn debut)

**Config:** docker · VUS=128 · 30s/test · best-of-3 · 1 dedicated CPU core per framework
(cpuset affinity) · granian+uvloop for ASGI · pyreqwest HTTP client everywhere.
**Change vs v2:** the whole Python field runs **Python 3.13.14** (pinned image) so
**Robyn** joins with its native `manylinux aarch64` cp313 wheel — no emulation, no
intra-Python version skew. (Robyn has no cp314 aarch64 wheel yet; revert to 3.14 when it
ships one.) All apps now use `uuid4` for response/entity ids (uuid7 is 3.14-only stdlib).
**gin / elysia:** NOT re-run — carried verbatim from v2 (the Python version can't affect
them). Marked † below. Raw JSON: `results/report-20260719T190353.json` · v2:
`FINAL-2026-07-16-vus128-v2-pyreqwest.md` · v1 (niquests): `FINAL-2026-07-15-vus128.md`

## Key findings
- **jero remains the #1 Python framework on all four tests** — third report in a row,
  now against a six-strong Python field.
- **Robyn debuts solidly mid-pack: 2nd Python on tests 2 & 4, 3rd on 1 & 3.** Its Rust
  server shows in footprint too — lowest Python memory by far (~50–70M vs ~80–110M).
- **Python 3.13 vs 3.14 (same code, v2→v3):** flat-to-slightly-faster on 3.13. jero and
  blacksheep ±0–3%; the pydantic-based apps gained more (fastapi +5–9%, litestar +5–9%,
  flask up to +14% on test 4) and every app's memory dropped ~15–20%. So v2's 3.14
  numbers were, if anything, mildly conservative for the pydantic frameworks.
- 100% success on all 24 framework×test blocks; zero port errors.
